# 甜星烘焙工作室 · 连锁烘焙店生日蛋糕定制与门店取货系统

一套面向**顾客端 / 门店制作端（裱花师 + 前台）/ 客服后台**三种操作节奏的生日蛋糕定制与取货协同系统。
技术栈：React 18 + TypeScript + Vite + Zustand（前端），Express + TypeScript（后端），JSON 文件持久化（命名卷），多阶段 Docker 镜像，`docker compose up -d` 一键部署。

---

## 原始需求

> 设计连锁烘焙店生日蛋糕定制与门店取货页面，可采用 React、TypeScript 和 Zustand。顾客下单时，页面展示尺寸、胚底、奶油、夹心、水果、过敏原、造型、题字、蜡烛餐具、取货门店和最晚修改时间，并采集生日对象、联系人、是否需要冷藏运输和发票信息。门店接单后，裱花师看到的是制作时间、原料准备、题字内容、造型参考和特殊禁忌；前台看到的是取货时段、支付状态和核验方式。若顾客临时改日期、题字含敏感内容、草莓缺货、门店冷柜容量不足、顾客要求换门店或取货后发现造型不符，页面要把顾客确认、客服说明、门店制作、裱花返工和费用调整落回原订单。交付前，门店上传成品照片、包装照片和冷藏提示；顾客取货签收后，售后窗口开始计算。页面还要让门店复盘哪些造型返工多、哪些原料导致改单多、哪些时段取货拥挤。页面还要适配顾客端、门店制作端和客服后台的不同操作节奏。顾客看到的是定制进度和可修改范围，门店看到的是原料、排班和取货压力，客服看到的是改期、退款和售后证据；三端状态一致，才能减少生日当天临时争议。

## 原始需求（本次新增功能：取货后造型申诉）

> 增加取货后造型申诉。顾客取货后上传照片认为造型不符，页面对比下单参考、门店成品照、签收时间和运输方式。客服可判定退款、补做、优惠券或拒绝赔付，结论进入门店造型质量统计。补做会重新生成制作排班和取货时间，优惠券则进入顾客账户并关联本次申诉原因。若运输造成变形，页面会区分门店责任和顾客自提责任。

### 功能落地说明

- **顾客取货后申诉**：已签收且在 24h 售后窗口内，顾客上传照片、选择问题类型（造型不符 / 题字错误 / 原料不符 / 运输变形 / 包装破损 / 食用不适 / 其他），并填写离店运输方式（冷链袋 / 常温携带）与历时。
- **页面证据对比**：客服判定台与顾客订单页并排呈现 ① 下单参考图、② 门店成品照、③ 顾客取货后照片，并附签收时间、取货时段、运输方式（冷链/常温）、顾客自述离店运输、包装与冷藏提示留存情况、制作期返工记录。
- **四种判定结论**：💸 退款（原路退回并联动支付状态）、🎂 补做、🎟️ 优惠券赔付、🚫 拒绝赔付；结论与说明全部落回原订单动态。
- **补做**：系统按新取货日期/时段**重新生成制作排班**（制作开始=时段前 2 小时，含次日冷柜容量校验），裱花师看板顶部出现「售后补做排班」，可推进 备料→制作→完成→取货，顾客端同步显示新取货时间。
- **优惠券**：自动进入顾客「🎟️ 优惠券账户」（券号、面额、90 天有效期），券面**关联本次申诉原因与原订单**，并标注责任归属。
- **运输变形责任区分**：判定时勾选「变形发生在离店后运输环节」，并明确 **门店责任**（包装/冷链交付过错）或 **顾客自提责任**（高温、久置、颠簸）；二者在统计中分别计入。
- **门店造型质量统计**：客服复盘看板新增「门店造型质量统计」——每店申诉数、门店责任占比、责任分布条、退款/补做/优惠券/拒绝数量与金额、运输变形起数、申诉原因分布、被申诉造型排行。

## 一键启动（宿主 Docker Compose）

```bash
# 环境变量由评测环境提供：CC_PUBLISH_PORT（宿主端口）、COMPOSE_PROJECT_NAME
cp .env.example .env        # 如环境已注入变量可跳过
docker compose up -d --build
# 查看实际映射端口
docker compose port app 8080
# 浏览器访问
http://host.docker.internal:<CC_PUBLISH_PORT>
# 健康检查（容器内自动执行）
docker compose ps
# 结束释放资源
docker compose down
```

- 仅应用服务发布到宿主端口 `${CC_PUBLISH_PORT}:8080`；本系统无外部数据库/缓存，业务数据保存在 compose 命名卷 `cake_data`（`/app/data/db.json`），不发布任何依赖端口。
- 镜像为多阶段构建，运行用户为非 root 用户 `app`，内置 `HEALTHCHECK`（轮询 `/api/bootstrap`）。
- 客服后台提供「↺ 重置演示数据」按钮，可随时恢复初始演示订单。

```bash
npm run dev:server   # 后端 tsx watch :8080
```

## 建议验证剧本（覆盖需求全部异常分支）

1. **顾客 `customer` 下单**：定制新蛋糕 → 草莓显示「库存紧张」→ 勾选过敏原规避 → 题字输入含「第一」（敏感词，提示转人工审核但可提交）→ 选冷链 → 填写生日对象/联系人/发票 → 提交。
2. **前台 `front`**：看到待接单订单；若当日冷柜已满，接单会被拦截并自动生成「冷柜容量不足」工单。
3. **裱花师 `baker`**：对 OD1001 登记原料准备 → 题字工单未确认前「开始制作」会被拦截 → 客服处理后再开制 →「报缺货」把草莓标记缺货，自动开缺货工单 →「登记返工」→ 上传**成品照片 + 包装照片 + 冷藏提示**，订单自动进入待取货。
4. **客服 `cs`**：在工单台对六类工单分别「给出方案」（替代水果/合规题字/错峰时段/跨店调货/售后退款），方案携带费用调整发送顾客。
5. **顾客 `customer`**：订单页看到红色「待您确认」横幅 → 同意后题字/水果/日期/门店与退款**落回原订单**；过最晚修改时间后可走「申请临时改期 / 换门店」工单。
6. **前台 `front`**：待取货订单中输入正确 4 位取货码（如 OD1001 = `8862`）→ 支付状态与冷藏提示校验通过后签收 → 售后窗口（24h）开始计算。
7. **售后（取货后造型申诉）**：用顾客 `customer` 打开 **OD1004**（今日已签收、常温自提的 3D 公仔，已带 1 条进行中的「运输途中变形」申诉）；也可在 **OD1003**（取货码 `5517`）窗口内自行「发起造型申诉」，上传照片并选择运输方式。切到客服 `cs` → 工单台「🛟 售后」→「证据对比并判定」，在并排比对下单参考图 / 门店成品照 / 顾客证据 + 签收时间 + 运输方式后，分别体验 **退款 / 补做 / 优惠券 / 拒绝赔付** 四种结论与门店/自提责任切换。
8. **补做闭环**：对申诉判定「补做」并选择新取货日期时段后，裱花师 `baker` 看板顶部出现「售后补做排班」，逐步推进 备料→制作→完成；顾客端订单页显示新取货时间。
9. **优惠券账户**：判定「优惠券」后，顾客 `customer2` 点右上角「🎟️ 优惠券账户」可看到券号、面额与**关联的申诉原因/原订单**（演示数据 OD1007 已预置一张 ¥50 券）。
10. **复盘看板（客服 → 门店复盘看板）**：查看新增的「门店造型质量统计」（各店退款/补做/优惠券/拒绝数量与金额、门店责任 vs 顾客自提责任分布、运输变形起数、申诉原因、被申诉造型排行），以及原有的造型返工、原料改单、时段拥挤热力、冷柜占用、工单类型分布。

| 需求点 | 实现位置 |

| 生日对象/联系人/冷链/发票信息采集 | 下单第 3 步 + 后端 `createOrder` 落库 |

| 前台视角：取货时段/支付状态/核验方式 | `src/pages/store/StoreFront.tsx`（时段拥挤、收银状态、取货码+尾号双因子核验） |
| 改日期 / 敏感题字 / 草莓缺货 / 冷柜不足 / 换门店 / 造型不符售后 | 六类工单 `ServiceCase`（`shared/types.ts`），引擎 `server/engine.ts`，客服工单台 `CSConsole.tsx` |
| 顾客确认、客服说明、门店制作、裱花返工、费用调整落回原订单 | 统一 `timeline` + `cases` + `fees` + `reworks`，所有动作走 `/api/orders/:id/action` 写同一订单；退款/加收联动支付状态 |
| 成品照片/包装照片/冷藏提示 | 裱花师上传（压缩存储），前台交付前强制校验冷链单冷藏提示 |
| 签收后售后窗口计算 | 24h 窗口，前台签收时刻起算，顾客端倒计时，逾期禁止发起 |
| 取货后造型申诉：照片对比（下单参考/门店成品/签收时间/运输方式） | 顾客 `CustomerOrderDetail.tsx` 申诉弹窗 + 客服 `AppealVerdictModal.tsx` 三图并排与签收/运输信息 |
| 客服判定退款/补做/优惠券/拒绝赔付 | `engine.afterSaleVerdict`，工单台与订单详情「证据对比并判定」 |
| 补做重新生成制作排班与取货时间 | `engine.scheduleRemake` + `RemakeAppointment`，裱花师看板「售后补做排班」`RemakeBoard` |
| 优惠券进入顾客账户并关联申诉原因 | `Coupon` + `/api/coupons`，顾客「优惠券账户」`CouponWallet` |
| 运输变形区分门店责任 / 顾客自提责任 | `AppealDecision.responsibility/transportDeformation`，判定台责任切换提示 |
| 结论进入门店造型质量统计 | `analytics().storeStyleQuality/appealByStyle`，复盘看板「门店造型质量统计」 |
| 复盘：造型返工 / 原料改单 / 取货拥挤 | `src/pages/cs/Analytics.tsx` + 后端 `analytics()` 聚合 |
| 三端状态一致 | 单一数据源、角色化视图、15s 轮询、乐观动作后即时刷新 |

## 目录结构

```
shared/types.ts          # 三端共用领域模型与状态枚举
server/
  index.ts               # Express 路由、角色鉴权、统一动作入口
  engine.ts              # 订单状态机、工单、费用、容量/库存校验、复盘聚合
  store.ts               # JSON 持久化、会话
  seed.ts                # 目录 / 门店 / 账号 / 演示订单
src/
  api.ts / store.ts      # API 客户端、Zustand 全局状态
  pages/customer/        # 顾客端
  pages/store/           # 裱花师 + 前台
  pages/cs/              # 客服工单台 + 复盘
Dockerfile               # 多阶段、非 root、HEALTHCHECK
docker-compose.yml       # 仅发布应用端口，数据命名卷
```
