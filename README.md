# 甜星烘焙工作室 · 连锁烘焙店生日蛋糕定制与门店取货系统

一套面向**顾客端 / 门店制作端（裱花师 + 前台）/ 客服后台**三种操作节奏的生日蛋糕定制与取货协同系统。
技术栈：React 18 + TypeScript + Vite + Zustand（前端），Express + TypeScript（后端），JSON 文件持久化（命名卷），多阶段 Docker 镜像，`docker compose up -d` 一键部署。

---

## 原始需求

### 初始需求（生日蛋糕定制与门店取货协同）

> 设计连锁烘焙店生日蛋糕定制与门店取货页面，可采用 React、TypeScript 和 Zustand。顾客下单时，页面展示尺寸、胚底、奶油、夹心、水果、过敏原、造型、题字、蜡烛餐具、取货门店和最晚修改时间，并采集生日对象、联系人、是否需要冷藏运输和发票信息。门店接单后，裱花师看到的是制作时间、原料准备、题字内容、造型参考和特殊禁忌；前台看到的是取货时段、支付状态和核验方式。若顾客临时改日期、题字含敏感内容、草莓缺货、门店冷柜容量不足、顾客要求换门店或取货后发现造型不符，页面要把顾客确认、客服说明、门店制作、裱花返工和费用调整落回原订单。交付前，门店上传成品照片、包装照片和冷藏提示；顾客取货签收后，售后窗口开始计算。页面还要让门店复盘哪些造型返工多、哪些原料导致改单多、哪些时段取货拥挤。页面还要适配顾客端、门店制作端和客服后台的不同操作节奏。顾客看到的是定制进度和可修改范围，门店看到的是原料、排班和取货压力，客服看到的是改期、退款和售后证据；三端状态一致，才能减少生日当天临时争议。

### 增量需求（取货后造型申诉）

> 增加取货后造型申诉。顾客取货后上传照片认为造型不符，页面对比下单参考、门店成品照、签收时间和运输方式。客服可判定退款、补做、优惠券或拒绝赔付，结论进入门店造型质量统计。补做会重新生成制作排班和取货时间，优惠券则进入顾客账户并关联本次申诉原因。若运输造成变形，页面会区分门店责任和顾客自提责任。

## 一键启动（宿主 Docker Compose）

```bash
# 环境变量由评测环境提供：CC_PUBLISH_PORT（宿主端口）、COMPOSE_PROJECT_NAME
cp .env.example .env        # 如环境已注入变量可跳过
docker compose up -d --build
# 查看实际映射端口
docker compose port app 8080
# 浏览器访问
http://host.docker.internal:<CC_PUBLISH_PORT>
# 健康检查（容器内自动执行）
docker compose ps
# 结束释放资源
docker compose down
```

- 仅应用服务发布到宿主端口 `${CC_PUBLISH_PORT}:8080`；本系统无外部数据库/缓存，业务数据保存在 compose 命名卷 `cake_data`（`/app/data/db.json`），不发布任何依赖端口。
- 镜像为多阶段构建，运行用户为非 root 用户 `app`，内置 `HEALTHCHECK`（轮询 `/api/bootstrap`）。
- 客服后台提供「↺ 重置演示数据」按钮，可随时恢复初始演示订单。

## 建议验证剧本（覆盖需求全部异常分支）

1. **顾客 `customer` 下单**：定制新蛋糕 → 草莓显示「库存紧张」→ 勾选过敏原规避 → 题字输入含「第一」（敏感词，提示转人工审核但可提交）→ 选冷链 → 填写生日对象/联系人/发票 → 提交。
2. **前台 `front`**：看到待接单订单；若当日冷柜已满，接单会被拦截并自动生成「冷柜容量不足」工单。
3. **裱花师 `baker`**：对 OD1001 登记原料准备 → 题字工单未确认前「开始制作」会被拦截 → 客服处理后再开制 →「报缺货」把草莓标记缺货，自动开缺货工单 →「登记返工」→ 上传**成品照片 + 包装照片 + 冷藏提示**，订单自动进入待取货。
4. **客服 `cs`**：在工单台对六类工单分别「给出方案」（替代水果/合规题字/错峰时段/跨店调货/售后退款），方案携带费用调整发送顾客。
5. **顾客 `customer`**：订单页看到红色「待您确认」横幅 → 同意后题字/水果/日期/门店与退款**落回原订单**；过最晚修改时间后可走「申请临时改期 / 换门店」工单。
6. **前台 `front`**：待取货订单中输入正确 4 位取货码（如 OD1001 = `8862`）→ 支付状态与冷藏提示校验通过后签收 → 售后窗口（24h）开始计算。
7. **售后**：演示订单 OD1003（取货码 `5517`，已签收且带一次返工）顾客端可在窗口内上传证据发起「造型不符」售后；客服核对成品/包装照片与证据后给出退款方案。
8. **复盘看板（客服 → 门店复盘看板）**：查看哪些造型返工多（含内部损耗金额）、哪些原料导致改单多、各门店各取货时段拥挤热力、冷柜占用、工单类型分布。

### 取货后造型申诉专项剧本（本次增量）

用两个浏览器分别登录顾客 `customer` / 客服 `cs`（裱花师 `baker`、前台 `front` 配合补做流程）。

1. **顾客发起申诉**：打开当天刚签收的 **OD1008**（取货码 `2756`，已签收约 3 小时、24h 窗口内）→「📸 发起取货后造型申诉」→ 选问题类型（造型不符/题字错误/配色偏差/装饰缺失/运输变形）、发现时机、上传取货后照片 → 提交。弹窗内直接并排展示①下单参考图②门店成品照③本次证据与签收时间、运输方式。
2. **客服判定**：客服台 →「🛟 取货后造型申诉」tab（待判定红点）→ 进入订单查看申诉面板：同一页对比**下单参考、门店成品照、签收时间、运输方式**与顾客证据 →「给出判定」：
   - 先选**责任归属**：门店制作责任 / 门店运输责任 / 顾客自提责任 / 无门店责任；
   - 再选**结论**：退款（原路退回、联动支付状态）/ 补做 / 优惠券 / 拒绝赔付。
3. **退款**：结论即时落回原订单（费用流水、时间线、支付状态），并计入该门店造型质量统计。
4. **优惠券**：券立即进入顾客账户（顾客顶栏「🎟️ 我的优惠券」可见），来源标注本订单与申诉原因，90 天有效。
5. **补做**：客服与顾客约定新取货日期/时段（页面实时显示该时段单量与当日冷柜占用）→ 确认后**重新生成制作排班**（建议开制=取货前 2 小时）与**新取货码**，订单退回「已接单」并清空旧照片 → 裱花师看板出现「🔁 申诉补做」标记，重新备料/开制/上传三照 → 前台按新取货码核验签收 → 申诉补做自动闭环。
6. **运输变形责任区分**：待判定的 **OD1004**（取货码 `7208`，冷藏自提、顾客逛商场 3 小时后融化）问题类型为「运输造成变形/融化」，客服只能在「门店运输责任 / 顾客自提责任」之间判；选顾客自提责任时结论自动锁定为「拒绝赔付」，且**不计入门店质量问题率**。**OD1005**（春熙里店、电动车自提倾倒）是一条已判定的自提责任拒赔历史单。
7. **质量统计**：客服「门店复盘看板」新增「门店造型质量统计」：按门店统计申诉数、待判定、门店责任、顾客自提责任、拒绝赔付、补做、退款/优惠券金额与**质量问题率（门店责任申诉 / 已交付单）**；并按造型聚合被申诉排行、责任分布与判决分布。

| 裱花师视角：制作时间/原料准备/题字/造型参考/特殊禁忌 | `src/pages/store/StoreBaker.tsx`、`StoreOrderDetail.tsx`（制作工单） |
| 前台视角：取货时段/支付状态/核验方式 | `src/pages/store/StoreFront.tsx`（时段拥挤、收银状态、取货码+尾号双因子核验） |
| 改日期 / 敏感题字 / 草莓缺货 / 冷柜不足 / 换门店 / 造型不符售后 | 六类工单 `ServiceCase`（`shared/types.ts`），引擎 `server/engine.ts`，客服工单台 `CSConsole.tsx` |
| 顾客确认、客服说明、门店制作、裱花返工、费用调整落回原订单 | 统一 `timeline` + `cases` + `fees` + `reworks`，所有动作走 `/api/orders/:id/action` 写同一订单；退款/加收联动支付状态 |
| 成品照片/包装照片/冷藏提示 | 裱花师上传（压缩存储），前台交付前强制校验冷链单冷藏提示 |
| 签收后售后窗口计算 | 24h 窗口，前台签收时刻起算，顾客端倒计时，逾期禁止发起 |
| 复盘：造型返工 / 原料改单 / 取货拥挤 | `src/pages/cs/Analytics.tsx` + 后端 `analytics()` 聚合 |
| 三端状态一致 | 单一数据源、角色化视图、15s 轮询、乐观动作后即时刷新 |
| 顾客取货后上传照片认为造型不符 | 顾客端 `StyleAppeal.tsx`（必传证据照 + 问题类型 + 发现时机），后端 `openStyleAppeal`，仅 24h 窗口内已签收订单可提交，快照四要素 |
| 页面对比下单参考、门店成品照、签收时间、运输方式 | 申诉弹窗/详情/客服面板同一页并排展示 `styleRefPhoto` / `storeFinalPhoto` / `evidencePhoto` + 签收时间 + 冷藏/常温运输方式 |
| 客服判定退款/补做/优惠券/拒绝赔付 | `csDecideAppeal`（`server/engine.ts`）+ 客服 `AppealPanel.tsx`；退款入费用流水联动支付、补做重排、优惠券入账户、拒赔留痕 |
| 结论进入门店造型质量统计 | `analytics().styleQuality`：按门店/造型聚合申诉数、责任分布、判决分布、退款/券/补做、质量问题率，`Analytics.tsx` 展示 |
| 补做重新生成制作排班和取货时间 | 补做判决重算取货日期/时段、取货前 2 小时开制时间、新取货码，订单退回备料并清空旧照片，裱花看板「🔁 申诉补做」，前台新码核验后回填补做签收 |
| 优惠券进入顾客账户并关联申诉原因 | `CustomerCoupon`（`state.coupons`）+ `/api/coupons`，券面标注订单号与申诉原因，顾客端「我的优惠券」 |
| 运输变形区分门店责任与顾客自提责任 | 责任枚举 `transport_store` / `transport_customer`（另有 `store`/`none`）；运输类问题强制二选一，自提责任自动锁定拒绝赔付且不计门店质量问题率 |

## 目录结构

```
shared/types.ts          # 三端共用领域模型：订单/工单/返工/取货后造型申诉/优惠券
server/
  index.ts               # Express 路由、角色鉴权、统一动作入口、/api/coupons
  engine.ts              # 订单状态机、工单、费用、容量校验、造型申诉判定（退款/补做/券/拒赔）、质量统计聚合
  store.ts               # JSON 持久化、会话、旧数据迁移
  seed.ts                # 目录 / 门店 / 账号 / 演示订单 / 申诉与优惠券种子（内联 SVG 示意图）
src/
  api.ts / store.ts      # API 客户端、Zustand 全局状态（含优惠券）
  pages/customer/        # 顾客端（StyleAppeal 申诉对比、Coupons 我的优惠券）
  pages/store/           # 裱花师 + 前台（补做单标记/新码核验）
  pages/cs/              # 客服工单台 + 申诉判定面板 + 复盘质量统计
Dockerfile               # 多阶段、非 root、HEALTHCHECK
docker-compose.yml       # 仅发布应用端口，数据命名卷
```
